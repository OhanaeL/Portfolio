The ✦ button in the corner of this page is sitepilot, an open-source library I wrote so a website can have an assistant that knows what is on the screen. Ask it "where are his projects?" and it scrolls to them and points; ask it to open the résumé and it does. This page is the demo, so everything below can be checked against the assistant you are looking at.

## The problem

A chat box bolted onto a website knows nothing about the page it sits on. It can answer from a prompt, but it cannot say "here", and it cannot open anything. Giving a model the raw page does not fix that: the DOM is huge, mostly layout, and full of things that should not be touched. And a website is usually static, while the model needs an API key that must never reach the browser.

The rule I designed around: **the site decides what the assistant may see and do, and the browser stays in charge of acting on it.**

## How it sees the page

Nothing is visible to the model unless the site opts it in, either with `data-pilot` attributes or, as on this site, with a manifest of CSS selectors generated from the same content that renders the page, so labels cannot drift from what is on screen.

- **Two tiers.** Landmarks such as sections, links and buttons are sent with every message. Repeated items such as project cards and timeline entries are fetched only when the model asks for them, so a long list never floods the prompt.
- **Stable keys.** Every element gets a key from its label ("Project card: Minesweeper Solver", "… #2" for a repeat), and the model can only act on a key it was given. It never invents a selector.
- **Hidden means hidden.** Anything `aria-hidden` or `inert` is left out, and every scan is capped.

## The loop runs in your browser

[figure:sitepilot-loop]

The assistant is a tool-calling loop, and it runs in the page. The browser builds the request from what is on screen, sends it, runs whatever tools come back (highlight an element, click it, search this portfolio), and repeats for up to 8 rounds per message. The tools are defined by the page, so a site adds its own: this one has a portfolio search.

The server is deliberately small. `createPilotHandler` is a stateless proxy that answers one round per request, so it runs anywhere a fetch handler does. Here it is a Cloudflare Worker, the only backend this static GitHub Pages site has, and it holds the keys.

## Jev answers the easy messages

Most of what visitors type is either a question I have already answered on this page or "show me X". Neither needs a large model. Before the LLM is called, the Worker asks [TypeSafe's](https://typesafe.ai) Jev, a model that returns typed judgments rather than text, a set of questions about the message in one call:

[figure:sitepilot-router]

- Is it about me or this site at all? If not, a short polite reply.
- Does one of my prepared answers cover it? Then that answer is sent as written.
- Is it a single action on one element, such as "open the résumé"? Then Jev picks the action and the element, the browser does it, and the reply is a fixed "Here it is." or "Done."

Only what none of those settle reaches the LLM. Open the eye view and each reply is labelled with who answered it: **Jev** or **LLM** with the model's name.

## Keeping a public endpoint safe

The Worker is a public URL, so it treats every request as untrusted:

- Only this site's origin is allowed, and the body is cut down to the messages and tool definitions; the model, the system prompt and the limits are fixed on the server.
- The browser sends a description of the page, not a prompt. The server writes the system prompt itself and drops any system message the browser sends.
- Message count and body size are capped, and images must be real image data or https URLs.
- Replies are rendered by a small markdown renderer that only links https, mailto and same-site paths, so a model cannot be talked into producing a `javascript:` link.
- Pressing stop aborts an action that is still in flight, so a click that was already on its way never lands.

## How it is built

sitepilot is a TypeScript monorepo of four packages: `core` (the headless loop, page scanning and actions, with no framework), `react` (a provider, a hook and the chat widget), `server` (the proxy and the Jev router hook), and `computer`, an optional plugin that lets a model see a rendered frame of only the opted-in elements and click by coordinates. It builds with Bun, is linted and formatted with Biome, and versions all four packages together with Changesets. CI runs the lint and the test suite on every pull request.
