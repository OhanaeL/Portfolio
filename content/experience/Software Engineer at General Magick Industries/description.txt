MagickMind is General Magick Industries' platform for AI agents. A product built on it can give its users agents that take part in shared chat rooms (we call them workspaces), remember past conversations, and act on what they are told. When I joined, an agent was mostly an illusion: one backend service answered on behalf of every agent, and the only memory an agent had was the memory of the person it was talking to. This case study is about turning that into something closer to a mind: an agent with its own identity, its own personality, its own memory and its own running process.

## The problem

- **One service answered for every agent.** It received each message, called the model, and posted the reply as "the assistant". A workspace could hold one agent, never several, and nothing an agent said could be traced to a specific agent.
- **Agents remembered nothing of their own.** When an agent needed context, the platform looked up the *human's* memories and the model played a character on top of them. Talk to the same agent in two rooms and it had no idea it had met you before.
- **The room owned the memories.** Memories were filed per workspace, summaries described the room's history from no one's point of view, and deleting a workspace deleted every memory formed in it. A one-person "private space" existed as a workaround for agents that could not remember.

The direction from the founder, in July: the basic unit should be the agent, not the room. An agent owns its memories, its personality and its history, and that bundle can walk into a workspace. His phrase for it was "minds, not group spaces".

## Options

Where should an agent live? Three shapes were considered.

1. **In a library on the customer's side.** Agents could connect to any platform, but our reasoning and memory code would have to leave our servers.
2. **Inside the existing service.** Nothing to deploy, but the one-agent, one-sender limits stay.
3. **As a real participant.** Each agent gets its own connection and identity and calls our backend for thinking and remembering. This is what we built.

Memory had its own ladder of options. The small step: file an agent's memories under the agent's own name instead of "assistant", and look them up as the agent as well as the user. The medium step: give each memory a point of view, so an agent's summary of a conversation is its own, not the room's. The large step: an agent that runs on its own and does its own remembering. The memory service took the small and medium steps; the supervisor took the large one.

## What I built

### Identity and process

The supervisor is the part of the platform that runs agents. Given an agent's definition, it issues that agent its own credentials, tied to one customer account, and starts it as a separate program built on Mindroid, the company's open-source Rust agent toolkit. The agent's identity is fixed at creation and cannot be changed by configuration. It joins a workspace the same way a person's app does, listening on the same channel and replying through the same endpoint. Every message it sends carries its own name. Several agents can share a room, and one that misbehaves can be stopped and restarted without disturbing the others.

[figure:before-after]

### Personality

Each agent loads its personality from the persona service, which my teammates built: a versioned set of traits that evolves per person the agent meets. The supervisor loads it when the agent starts and keeps it for the life of the process, so personality belongs to the agent, not to whichever room it is in.

### Memory

In the memory service I gave agents their own point of view. Each memory now records whose memory it is. An agent can look back through its own memories as well as the user's, and can ask what happened in a given period across every room it has been in. Every lookup is limited to one customer account, so an agent that serves several customers keeps their memories apart. Summaries of one-to-one conversations name who said what, and the same message can no longer be filed twice. When a turn starts, the agent remembers twice: what it knows about this person, and what it learned the last time it was here.

### The turn

With identity, personality and memory in place, each conversation turn is the agent's own loop. It can call tools directly instead of having tool requests fished out of model text. A cheap, fast model answers most turns and hands the same turn, with the same context, to a stronger model when it is not confident. The hand-off is a single yes/no field in one required tool call, so the small model has only one way to answer.

## Results

- Several agents can share a workspace, each with its own identity, and every message is attributed to the agent that sent it. Group rooms with people and several agents now make sense: an agent can answer a person, answer another agent, or stay quiet, and everyone in the room can see who said what.
- An agent remembers the people it has met across rooms. Its own memory and the user's memory are looked up on the same system.
- A turn takes 2.5 seconds instead of 4 after caching in the execution loop. The fastest path through the reasoning service is 40% quicker after I reworked how requests are put together.
- The reasoning strategies I added on that path (RLM, Lambda-RLM, a panel of judges and tree search) score 22 to 34 points above a plain model call on GPQA, a graduate-level science benchmark, with the same model.
- Since joining I have been the top committer on the memory, reasoning and supervisor services, and a contributor to Mindroid and the Python SDK.

## What is not done

The room still owns the timeline. An agent's memories carry its name, but they are not yet linked into one life story across rooms, and deleting a workspace still deletes what happened in it. The next steps in the design are to separate memory from the room's lifecycle, keep one timeline per agent, make the agent's own point of view the default when summarising, and record what an agent has read. The interface those steps need, "as agent X: remember, recall, reflect, read", is the same one a self-hosted Mindroid agent already uses, so the platform and the open-source runtime are converging on one design.

## Looking back

The fix that mattered most was also the smallest, and I did it last. Every agent's messages were filed as "assistant" because of a single hard-coded sender. That was not carelessness; it is how the chat protocol every model provider uses works. A conversation has three roles, system, user and assistant, and every framework built on it files the model's reply under the third. Following the standard meant no agent could have a name of its own. Giving each agent its own user identity went against that default, and every other piece of this work depended on it: none of the memory changes could show a visible result until agents had names. It is done now, and it is what made mixed rooms of people and agents work at all: once an agent is a named participant, a conversation between two agents and a human is the same kind of conversation as one between three humans. If I were starting over I would make that change on day one and build the supervisor on top of it, instead of building the supervisor first and discovering the missing name underneath.
