MagickMind is General Magick Industries' platform for AI agents. A product built on it can give its users agents that take part in shared chat rooms, remember past conversations, and act on what they are told. Each agent runs as its own process with its own identity, and joins a room the way a person's app does. Once agents worked that way, the question became how long people had to wait for them. This case study is about that wait: where the time in an agent's turn went, and what I did about it.

## What a turn does

When a message arrives, the agent reads its context (the room's recent history, its personality and what it remembers about the people in the room), sends that to a model through the AI inference service, runs any tools the model asks for, and posts its reply. Every one of those steps can make a person wait.

## Where the time went

- **Every question took the slow path.** An easy question went through the same heavyweight reasoning as a hard one, so a greeting could cost as much as a research question.
- **The AI inference service queued requests.** It served requests on a fixed pool of ten threads. Under load, a request waited for a free thread before any work started.
- **A turn did everything in order.** It fetched history, then the personality, then called the model, even though none of those steps needed the others' results.
- **Tool calls were parsed out of model text.** Models drifted from the expected format, so calls were missed and raw tool syntax sometimes reached the chat as the agent's reply.
- **Memory search sometimes hung.** When the embedding provider stalled, a search waited 30–60 seconds, and the agent either answered late or said its memory had failed.

## What I changed

### Answer easy turns with a fast model

A cheap, fast model takes every turn first. It either answers or hands the same turn, with the same context, to a stronger model. The hand-off is a single yes/no field in one required tool call, so the small model has only one way to answer. When it does hand off, it posts a short holding line in the agent's own voice first, so the room is never silent. In testing, a simple question came back in 2.6 seconds.

### Move the AI inference service to async

I migrated the AI inference service from a synchronous server on ten threads to an async one. Older blocking code still runs, but on a bounded pool of its own, off the main loop, with a cap on concurrent requests so the service pushes back instead of falling over. Under load, a request no longer waits for one of ten threads to free up.

### Take work off the critical path

Anything the model's answer does not depend on now runs at the same time as the model call. While the model writes its reply, the agent already re-reads the room's history for the next turn. On a turn with nothing cached, the personality and the history are fetched together, so the turn waits for the slower of the two instead of both. When the model asks for several tools in one step, they run at once, and their results still go back in the order the model asked for them. Messages that arrive while a turn is running are merged into one follow-up instead of queuing a turn each.

### Cache the context

Each room's prepared context is cached, so most turns start without fetching anything. The refresh that runs during the model call keeps the cache current, and the agent's own reply is added to it afterwards, because the refresh started before that reply existed. The same rework moved agents to the newer inference route, which skips a verification pass the old route ran before every answer. Together, these took a turn from 11 seconds to 3.8.

### Replace text-parsed tool calls with native ones

I moved tool calling to the model's native format across the gateway, the AI inference service and the agent runtime. In a benchmark, correct tool calls went from 61% to 100%, and the slowest turns dropped from 4.2 seconds to 3.2.

### Put a ceiling on memory search

Query embeddings now get their own client with a 2-second timeout and two retries, and search falls back to keyword matching when the vector side cannot answer in time. Against the development environment, 9 of 10 embeddings came back in 0.5–6.6 seconds and the tenth gave up at 7.4, instead of hanging for up to a minute. Separately, a short memory policy tells the agent to look things up for anything that depends on a shared past and to skip lookups for small talk. With that and parallel tool calls, over 44 live turns, the median answer to a memory question went from 11.8 seconds to 5.0.

## Keeping the cache correct

The hard part of the cache was keeping it right, not making it fast.

- **The refresh is awaited, never left running in the background.** Otherwise it could land after the reply was added and overwrite it with history from before the reply existed.
- **A stale refresh loses.** A message the agent stays silent on clears the room's entry. A refresh that started before that would put the old history back, so each entry carries a generation number, and a refresh whose generation has moved on is dropped.
- **Replayed text is escaped exactly like fetched text.** A reply added to the cache goes back into the prompt as the agent's own words. If it skipped the escaping the normal path applies, the cache would become a way to inject instructions. A test checks the two paths produce identical text.
- **The cache is bounded.** It keeps 64 rooms and evicts the one touched least recently.

## Results

- A turn takes 3.8 seconds instead of 11.
- Refactoring the AI inference service cut end-to-end model turn time by 40%.
- Correct tool calls went from 61% to 100%, and the slowest turns from 4.2 seconds to 3.2.
- Memory search has a worst case of about 7 seconds instead of 30–60-second hangs, and the median memory answer went from 11.8 seconds to 5.0.
- Since joining I have closed 110+ tickets, and I contribute to Mindroid, the company's open-source Rust agent toolkit.

## Looking back

I expected our own code to be the slow part. When I measured a turn, the model call was 98.7% of it, and fetching context took 19 milliseconds. Shaving our own calls still mattered for the turns that followed, but the biggest wins came from not asking the model for work it did not need to do: a fast model for easy questions, and no verification pass before every answer. If I started again, I would measure where a turn's time goes on day one, before deciding what to optimise.
